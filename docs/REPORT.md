# Отчёт о проекте «Контур»

## Постановка задачи

Разработать распределённую программную систему для исследования температурных временных рядов оборудования. Система должна поддерживать загрузку данных, обучение модели нормального поведения, обнаружение аномалий и воспроизводимое представление результатов.

Проект связан с исследовательской работой по обнаружению отклонений в показаниях климатического оборудования. Пользователи — исследователь и инженер, работающие с архивом датчиков. Разработка выполняется индивидуально.

## Пользовательские сценарии

1. Пользователь получает последовательные порции заранее собранных данных либо загружает CSV. Результат — сохранённый набор, список датчиков и сведения о качестве данных.
2. Пользователь выбирает датчик и периоды нормальной работы, запускает обучение и получает сохранённую версию модели.
3. Пользователь применяет модель к последующему периоду. Результат — интерактивные графики сигнала, реконструкции и оценок аномальности.
4. Пользователь оценивает срабатывания по разметке и скачивает автономный HTML-отчёт или таблицу результатов.
5. Пользователь открывает ранее сохранённый запуск и воспроизводит его представление без повторного расчёта.

## Архитектура и технологии

Система содержит пять отдельных Docker-контейнеров: Collector, Storage, ML Service, Web Master и Visualization. Каждый сервис предоставляет Python/FastAPI API, `/health`, OpenAPI, конфигурацию JSON и журналирование запросов. Docker Compose задаёт сеть, зависимости готовности и постоянные тома.

Collector выдаёт батчи из подготовленного CSV. Web Master управляет смещением и сохраняет выданные записи через Storage. SQLite принадлежит только Storage. ML Service обращается к данным через Storage API и самостоятельно сохраняет версии весов. Visualization передаёт действия пользователя Web Master; вычислений обучения внутри интерфейса нет.

SQLite выбран для простого локального развёртывания и транзакционного хранения. Обособление через API позволяет позже заменить СУБД без изменения интерфейса и алгоритма. Файловые версии моделей достаточны для первой версии; тяжёлая внешняя MLOps-платформа не используется.

Для визуализации применены HTML/CSS/JavaScript и локальная копия Plotly.js, обслуживаемые Python-сервисом. Отчёт не зависит от CDN и содержит встроенные SVG-графики. Его можно открыть без работающего сервера и сохранить в PDF средствами браузера.

## Данные и подготовка

Исходные исследовательские файлы содержат 426 638 измерений и соответствующую разметку трёх температурных датчиков. Демонстрационная производная содержит 38 016 записей с шагом 10 минут за период с 13 июня по 8 сентября 2025 года. Для интервала (t−10 минут,t] вычисляются среднее температуры и максимум метки аномалии. Временная отметка соответствует правому краю, что сохраняет причинность. Исходные файлы не изменяются.

Пропуски сохранены, всего 126 значений и 126 меток. Неизвестная метка не приравнивается к норме при оценке качества. Для собственного CSV поддерживаются явные пропуски, регулярный шаг, несколько датчиков и необязательная разметка. Хэши и точное описание преобразования включены в `data/demo_manifest.json`.

## Алгоритм

Использован адаптированный LSTM-автоэнкодер из исследовательского проекта пользователя: кодировщик, латентное представление размерности 8, декодировщик и выходная линейная проекция. Скрытая размерность 32. Обучение — Adam с MSE. Система использует CPU, фиксированный seed и детерминированные операции.

Обучающий период делится по времени в отношении 80/20: первая часть для градиентного обучения, вторая для выбора лучшей эпохи. Окна не пересекают эту границу. Median/IQR-нормализация рассчитывается только на обучающей части. При известной разметке обучающие и калибровочные окна должны полностью состоять из нормальных точек. Без разметки нормальность выбранного периода является предположением пользователя.

Основной score — квадрат ошибки последней точки окна после нормализации. Ни будущие значения, ни усреднение ошибок будущих окон для текущей точки не применяются. Окна с нечисловыми значениями и разрывом шага исключаются. Порог фиксируется по квантилю 0.99 ошибок отдельного последующего периода.

Демонстрационные периоды: обучение [13.06,22.06), калибровка [22.06,29.06), проверка [20.07,09.09) 2025 года. Начало проверки должно быть не раньше окончания калибровки. Качество оценивается только на точках с доступными score и разметкой. Выводятся precision, recall, F1, F0.5, F2, AP, ROC AUC и матрица ошибок. Неопределённые метрики явно обозначаются.

## Воспроизводимость и ошибки

Каждая версия сохраняет веса, параметры, seed, историю потерь, порог, хэш снимка данных, шаг и версию PyTorch. Изменение измерений исходного набора после обучения делает применение прежней версии недопустимым. Незавершённое обучение после перезапуска отмечается как прерванное. Данные и результаты сохраняются в SQLite; веса и summary — в отдельном томе ML Service.

Ввод проверяется по схемам, превышение лимитов и недоступность зависимостей обрабатываются понятными сообщениями. Фоновое обучение освобождает HTTP-сервис для опроса прогресса. Система ограничивает одновременное выполнение ресурсоёмких операций одним заданием.

## Ограничения

Использованные периоды ранее участвовали в исследовательских экспериментах, поэтому демонстрация не является независимой внешней валидацией. Результаты этой адаптации нельзя подменять прежними метриками исходной модели. Система обнаруживает аномальные точки, но не измеряет время предупреждения до начала реальной неисправности.

В первой версии отсутствуют роли пользователей, внешний онлайн-источник, распределённая очередь и несколько типов моделей. Они могут быть добавлены после промежуточной проверки. Запуск и демонстрация описаны в README и `docs/DEMO.md`; фактические проверки — в `docs/VALIDATION.md`.
